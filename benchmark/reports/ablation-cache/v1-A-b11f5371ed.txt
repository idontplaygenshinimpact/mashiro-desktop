这道题是前端/后端面试的高频题，核心是考察你对 HTTP 缓存机制的整体理解，以及是否能把“强缓存”“协商缓存”“Cache-Control”“ETag/Last-Modified”这些概念串成一条完整链路。

下面按“总-分-总”的方式讲解。

---

## 一、HTTP 缓存解决什么问题？

HTTP 缓存是为了减少重复请求、降低网络消耗、加快页面加载速度。浏览器会优先使用本地缓存，缓存失效后再与服务器验证资源是否真的变了。

HTTP 缓存主要分为两类：

- **强缓存**：不发请求，直接用本地缓存。
- **协商缓存**：发请求给服务器，让服务器判断能否继续用缓存。

---

## 二、强缓存与协商缓存的区别

### 1. 强缓存

浏览器发现资源还在“新鲜度”内，直接使用本地缓存，不发送任何 HTTP 请求。

- 响应头字段：
  - `Expires`
  - `Cache-Control: max-age=...`
- 命中表现：
  - DevTools 中显示 `200 OK (from disk cache)` 或 `200 OK (from memory cache)`

### 2. 协商缓存

浏览器发现强缓存已过期，于是携带校验信息请求服务器。

- 如果资源没有变化，服务器返回 `304 Not Modified`，浏览器继续用缓存。
- 如果资源变化了，服务器返回 `200 OK` 和新的响应体，浏览器更新缓存。

- 响应头字段：
  - `Last-Modified`
  - `ETag`
- 请求头字段：
  - `If-Modified-Since`
  - `If-None-Match`

### 3. 区别对比

| 对比项 | 强缓存 | 协商缓存 |
| --- | --- | --- |
| 是否发请求 | 不发请求 | 会发请求 |
| 命中状态 | 200（from cache） | 304 Not Modified |
| 判断依据 | 时间是否过期 | 资源是否变化 |
| 核心响应头 | Expires / Cache-Control | Last-Modified / ETag |
| 谁决定是否命中 | 浏览器本地判断 | 服务器判断 |

一句话总结：

> 强缓存判断“有没有过期”，协商缓存判断“有没有变化”。

---

## 三、Cache-Control 指令

`Cache-Control` 是 HTTP/1.1 中最重要的缓存控制字段，同时支持请求头和响应头。

### 1. 可缓存性指令

| 指令 | 含义 |
| --- | --- |
| `public` | 响应可以被浏览器和中间代理/CDN 缓存 |
| `private` | 响应只能被浏览器缓存，代理不能缓存，适合带用户隐私的数据 |
| `no-cache` | 可以缓存，但使用前必须去服务器验证，相当于强制走协商缓存 |
| `no-store` | 完全不允许缓存，每次都要重新请求 |

注意：

- `no-cache` 不是“不缓存”，而是“缓存前必须验证”。
- `no-store` 才是真正的不缓存。

### 2. 过期时间指令

| 指令 | 含义 |
| --- | --- |
| `max-age=<seconds>` | 相对当前时间的缓存有效期，比如 `max-age=31536000` 代表一年 |
| `s-maxage=<seconds>` | CDN/代理服务器生效，覆盖 `max-age`，浏览器忽略 |
| `Expires` | HTTP/1.0 的绝对过期时间，优先级低于 `Cache-Control`，两者同时存在时以 `Cache-Control` 为准 |

### 3. 重新验证/其他指令

| 指令 | 含义 |
| --- | --- |
| `must-revalidate` | 缓存过期后必须回源验证，如果服务器不可用，不可以直接使用过期缓存 |
| `proxy-revalidate` | 类似 `must-revalidate`，对代理缓存生效 |
| `immutable` | 配合长缓存使用，表示过期时间内内容不会变，刷新页面时也不需要重新验证 |
| `max-stale` | 请求方允许使用已过期的缓存 |
| `min-fresh` | 请求方要求资源至少在多少秒内还保持新鲜 |
| `only-if-cached` | 只用缓存，不发网络请求 |

### 4. 常见的 Cache-Control 配置示例

```http
# 静态资源：缓存一年
Cache-Control: public, max-age=31536000, immutable

# HTML 页面：每次都要验证
Cache-Control: no-cache

# 动态接口：绝不缓存
Cache-Control: no-store
```

## 四、Last-Modified / ETag 的工作方式

### 1. Last-Modified + If-Modified-Since

这是基于“时间”的协商缓存。

#### 工作流程

1. 第一次请求资源。
2. 服务器响应头中返回：

```http
Last-Modified: Wed, 21 Oct 2024 07:28:00 GMT
```

3. 浏览器缓存这个资源和时间。

4. 强缓存过期后，浏览器再次请求，自动带上：

```http
If-Modified-Since: Wed, 21 Oct 2024 07:28:00 GMT
```

5. 服务器根据这个时间判断：

- 资源在这个时间之后**没有修改过**，返回 `304 Not Modified`。
- 资源在这个时间之后**修改过**，返回 `200 OK` 和新的资源，同时更新 `Last-Modified`。

### 2. ETag + If-None-Match

这是基于“内容标识”的协商缓存。

`ETag` 是服务器为资源生成的唯一标识，通常是哈希值或版本号。

#### 工作流程

1. 第一次请求资源。
2. 服务器响应头中返回：

```http
ETag: "33a64df55130f6e4e6b9d8b8f9d0f0c2"
```

3. 强缓存过期后，浏览器再次请求，自动带上：

```http
If-None-Match: "33a64df55130f6e4e6b9d8b8f9d0f0c2"
```

4. 服务器比较当前资源的 `ETag` 和请求头中的 `ETag`：

- 相同，返回 `304 Not Modified`。
- 不同，返回 `200 OK` 和新资源，并更新 `ETag`。

### 3. 为什么需要 ETag？

`Last-Modified` 有几个缺陷：

- 修改时间只能精确到秒，极短时间内的修改可能感知不到。
- 文件修改时间变了，但内容没变，会白白触发重新下载。
- 某些服务器无法准确获取文件的最后修改时间。

`ETag` 则可以精确判断内容是否真的变化。

如果服务器同时返回了 `ETag` 和 `Last-Modified`，浏览器会同时携带 `If-None-Match` 和 `If-Modified-Since`，但服务器会**优先校验 ETag**。

## 五、完整的 HTTP 缓存流程

整个流程可以用下面这张图概括：

```
浏览器发起请求
        │
        ▼
检查强缓存（Cache-Control: max-age / Expires）
        │
   ┌────┴─────┐
   │          │
   │ 未过期   │ 已过期
   │          │
   ▼          ▼
直接用本地缓存  携带 If-None-Match / If-Modified-Since
(200 from cache)        │
                        ▼
                  服务器判断资源是否变化
                        │
              ┌─────────┴─────────┐
              │                   │
            未变化              变化了
              │                   │
              ▼                   ▼
       返回 304              返回 200 + 新资源
       继续用本地缓存         更新本地缓存
```

## 六、补充注意点

1. `Cache-Control: no-cache` 不是不缓存，而是每次都走协商缓存。
2. `Cache-Control` 的优先级高于 `Expires`。
3. 如果服务器没有返回任何缓存控制字段，浏览器可能使用启发式缓存算法，例如根据 `Last-Modified` 到当前时间的 10% 作为过期时间。
4. 前端工程化中，通常给带 hash 的静态资源设置长缓存：

```http
Cache-Control: public, max-age=31536000, immutable
```

5. 对于 HTML 页面，通常设置：

```http
Cache-Control: no-cache
```

这样能保证页面内容更新，同时静态资源还能利用缓存。

---

如果要一句话回答面试官：

> HTTP 缓存分为强缓存和协商缓存。强缓存通过 `Cache-Control` 和 `Expires` 控制，缓存未过期时直接使用本地缓存，不发请求。协商缓存通过 `ETag` / `Last-Modified` 和控制请求头 `If-None-Match` / `If-Modified-Since` 实现，当强缓存过期后请求服务器验证资源是否变化，未变化返回 `304`，变化返回 `200` 和新资源。其中 `Cache-Control` 是更现代、更灵活的缓存控制方式，而 `ETag` 比 `Last-Modified` 更精准，两者同时存在时优先用 `ETag`。
