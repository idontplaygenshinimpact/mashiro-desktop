## 一、Hooks 的底层实现：链表结构

React 源码中，每个组件都有一个对应的 **Fiber 节点**。Fiber 节点上保存了组件的状态、副作用等信息。对于函数组件，Fiber 上有一个 `memoizedState` 属性，它指向**一条 Hooks 链表**。

每次组件渲染时，React 会按照 **Hooks 的调用顺序** 依次创建或复用链表中的 Hook 节点。每个 Hook 节点大致结构如下（简化）：

```js
{
  queue: ...,        // 更新队列（如 useState 的更新 action）
  memoizedState: ..., // 当前状态值（useState 的值 / useRef 的 current / useEffect 的 effect 对象）
  next: null          // 指向下一个 Hook
}
```

### useState 的执行过程

1. **首次渲染**：按调用顺序创建 Hook 节点，并将状态存入 `memoizedState`，然后串成链表。
2. **更新渲染**：React 会从链表的第一个节点开始，按顺序逐个取出对应的 Hook，读取上一次的 `memoizedState`，并计算新的状态。

React 内部通过一个全局的“当前正在渲染的 Fiber 指针”和“下一个要执行的 Hook 指针”来遍历链表。调用 `useState` 时，本质上就是“取当前指针指向的节点，然后指针后移”。

### 关键点

- Hooks 是**按顺序**和**数量**在每次渲染时保持一致的。
- 链表的作用就是**保存状态**，并且让 React 知道“第几个 useState 对应哪个状态”。

## 二、为什么 useState 不能写在条件语句中

因为 React 依赖 **调用顺序** 来匹配 Hooks。

假设你写了这样的代码：

```js
function Component({ condition }) {
  const [a, setA] = useState(0);
  if (condition) {
    const [b, setB] = useState(1); // ❌
  }
  const [c, setC] = useState(2);
  return null;
}
```

### 问题分析

- 第一次渲染时，`condition` 为 `true`，链表为：a → b → c。
- 第二次渲染时，`condition` 变为 `false`，此时 b 没有被调用，链表只剩：a → c。
- React 在第二次渲染时，会按顺序匹配：
  - 第一个 useState 拿到的是 a 的状态，没问题。
  - 第二个 useState（也就是代码里的 c）想去拿链表第二个节点的状态，但链表第二个节点其实是上一次的 b 的状态（`1`），而不是 c 对应的 `2`。
  - 结果：**状态错乱**，甚至可能导致出现运行时错误。

### React 的官方规则

React 要求 Hooks **必须在组件顶层调用**，不能放在条件、循环、嵌套函数中。核心原因就是：**React 没有“键名”来标识每个 Hook，它依赖的是稳定的调用顺序**。只要顺序不变，React 就能把每次的状态正确对应到同一个 Hook。

> 其实也可以通过 Map 等方式用 key 来标识 Hook，但 React 选择了更简单的数组/链表方案，保证了性能和可预测性。

### 面试加分点

你可以补充：**React 官方 ESLint 规则 `react-hooks/rules-of-hooks` 就是用来在编译期发现这种问题的**。另外，如果你确实需要条件控制，可以把条件放在组件内部的其他逻辑里，或者拆分子组件。

## 三、闭包陷阱的本质与规避

### 什么是闭包陷阱？

常见场景：在 `useEffect` 或异步回调中，读取了某个 state 的值，但读取到的却是**旧的渲染**中的值。

例如：

```js
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      console.log(count); // 永远打印 0
      setCount(count + 1); // 永远把 count 设为 0 + 1
    }, 1000);
    return () => clearInterval(timer);
  }, []);
}
```

这里 `useEffect` 的回调闭包捕获了**第一次渲染时的 `count = 0`**。由于依赖数组为 `[]`，effect 不会重新执行，所以闭包里的 `count` 永远都是 0。

### 原因

- 每次渲染都有自己的 props 和 state，它们是不可变的常量。
- 函数组件每次渲染都会生成一个新的闭包，闭包内捕获的是当前渲染时的值。
- 如果 `useEffect` 只执行一次（空依赖），它捕获的就是**首次渲染**的闭包。
- 如果依赖数组没有包含某个变量，effect 就不会因为该变量变化而重新创建闭包，所以读到的始终是旧值。

### 如何解决闭包陷阱？

1. **正确设置依赖数组**：

```js
useEffect(() => {
  const timer = setInterval(() => {
    setCount(c => c + 1); // 使用函数式更新，不依赖外部 count
  }, 1000);
  return () => clearInterval(timer);
}, []); // 不需要依赖 count，因为使用了函数式更新
```

但如果你需要在回调里读取当前 `count`（比如打印），就必须把 `count` 加进依赖：

```js
useEffect(() => {
  console.log(count);
}, [count]);
```

2. **使用 `useRef` 保存最新值**：

```js
const countRef = useRef(0);
countRef.current = count; // 每次渲染更新 ref

useEffect(() => {
  const timer = setInterval(() => {
    console.log(countRef.current); // 拿到最新值
  }, 1000);
  return () => clearInterval(timer);
}, []);
```

3. **使用函数式更新**（适用于 `setState` 操作）：

```js
setCount(prev => prev + 1); // 不依赖外部变量，永远基于最新值
```

4. **`useLatest` 自定义 Hook**（封装 `useRef` 的模式）

### 面试加分点：闭包陷阱与 Hooks 链表的关联

- 闭包陷阱并不是链表的问题，而是 **JavaScript 闭包特性 + React 渲染模型** 共同作用的结果。
- 可以对比 `class` 组件：`this.state` 是可变对象，所以异步回调中总能通过 `this` 拿到最新状态；而函数组件每次渲染的 state 都是常量，闭包捕获的是“某个渲染时刻”的快照。
- React 官方也在文档中强调：“每个渲染都有它自己的 props 和 state”，理解这一点是理解闭包陷阱的关键。

## 总结

| 问题 | 核心答案 |
|------|----------|
| Hooks 实现原理 | Fiber 上保存 Hooks 链表，React 按调用顺序遍历链表，`memoizedState` 存储状态 |
| 为什么不能写在条件语句中 | 破坏 Hooks 调用顺序，导致状态错位，引发 bug |
| Hooks 链表如何工作 | 首次渲染创建节点链，更新时按顺序复用节点，读取/更新状态 |
| 闭包陷阱 | 闭包捕获了旧渲染的值，因为 effect 只执行一次或依赖不完整；可通过依赖、useRef、函数式更新解决 |

面试时如果能结合简单代码示例，并说出“渲染快照”和“状态错位”这两个关键短语，会显得你对 React 原理理解很扎实。祝你面试顺利！
