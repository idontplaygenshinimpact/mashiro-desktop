## 题目

外部面经中有一道前端经典面试题，要求：

1. 解释浏览器事件循环的宏任务 / 微任务机制；
2. 给出以下代码的输出顺序及原因：

```javascript
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
```

这道题代码虽短，却完整考察了浏览器事件循环模型、同步/异步边界、宏任务与微任务的优先级关系。以下提炼为两个核心问题逐一讲解。

---

### 问题 1：什么是宏任务 / 微任务？浏览器事件循环到底如何调度它们？

#### 结论

事件循环的调度规则是：**每一轮循环只从宏任务队列中取出一个任务执行，执行完当前宏任务后必须把微任务队列清空（包括这期间新产生的微任务），然后才可能进入渲染或取出下一个宏任务**。因此微任务的执行优先级永远高于宏任务。

#### 原理

浏览器主线程是单线程的，JS 代码和渲染共用一条线程，所以需要一套调度机制来安排任务的执行顺序——这就是事件循环（Event Loop）。任务按类型分成两大类：

- **宏任务（MacroTask / Task）**：由宿主环境发起的任务，例如 `setTimeout`、`setInterval`、`I/O`、UI 事件、`MessageChannel`、`setImmediate`（Node 独有）。浏览器维护一个宏任务队列，**每轮事件循环只取一个宏任务执行**。
- **微任务（MicroTask / Job）**：由 JS 引擎内部发起的任务，例如 `Promise.then / catch / finally`、`queueMicrotask`、`MutationObserver`、`async / await` 的后续代码。微任务有自己的微任务队列，**在一个宏任务结束后、下一个宏任务开始前，必须被全部清空**。

一个更完整的事件循环“一轮”（Tick）可以简化为：

```text
执行一个宏任务
  └─> 执行该宏任务期间的同步代码
  └─> 执行微任务队列（直到清空，期间新加入的微任务也会执行）
  └─> 执行渲染（rAF、样式计算、绘制等）
  └─> 取下一个宏任务
```

**为什么微任务要有“VIP 通道”？** 核心原因是**保证异步回调的响应性与状态一致性**。例如 Promise 的 `.then` 回调如果排成宏任务，就必须和 `setTimeout`、用户点击事件一起排队，延迟可能很大；而微任务可以让异步回调在“当前宏任务结束后、渲染开始前”立刻执行，减少不必要的等待和状态不一致。这也是 Vue 的 `nextTick`、React 的批量更新调度大量使用微任务（或等价机制）的原因。

| 维度 | 宏任务（Task） | 微任务（MicroTask） |
|------|--------------|-------------------|
| 典型来源 | `setTimeout`、`I/O`、UI 事件 | `Promise.then`、`queueMicrotask`、`MutationObserver` |
| 执行优先级 | 低 | 高 |
| 每轮循环取出数量 | 1 个 | 队列全部清空 |
| 执行时机 | 新的一轮循环开始 | 当前宏任务结束后立即执行 |
| 是否会插入渲染 | 宏任务之间可能穿插渲染 | 微任务全部执行完才可能渲染 |

#### 实现

无代码，纯概念。事件循环的调序过程可以用以下执行流程对照表示：

```text
宏任务 A 开始
  → A 中产生宏任务 B（入队）
  → A 中产生微任务 M1、M2（入队）
宏任务 A 结束
  → 立即依次执行 M1、M2
  → 若 M1/M2 执行中又产生 M3，则继续执行 M3
  → 微任务队列为空
  → 走到渲染阶段（由浏览器决定是否真的渲染）
宏任务 B 开始
  → ...
```

#### 边界与追问

- **微任务饥饿（Starvation）**：如果在微任务中不断加入新的微任务，就会导致微任务队列永远清不空，后续宏任务（包括 `setTimeout`、点击回调）永远得不到执行，页面表现为卡死。事件循环只能保证“每轮宏任务后清空微任务”，无法防止程序员写出死循环式的微任务。
- **追问 1：`requestAnimationFrame` 是宏任务还是微任务？** 两者都不是。rAF 的回调在“本轮宏任务 + 微任务处理完之后、浏览器做渲染之前”执行，是与屏幕刷新率（如 60Hz/120Hz）同步的独立渲染任务。
- **追问 2：Node.js 事件循环跟浏览器完全一样吗？** 不完全一样。Node 基于 libuv 的阶段式循环（`timers → pending → poll → check → close`），且 `process.nextTick` 的优先级高于 Promise。但“微任务优先于宏任务”的核心理念一致。
- **追问 3：宏任务的划分是 ECMAScript 规范还是 HTML 规范定义的？** ECMAScript 规范定义了 “Job”（即微任务）和 Promise 的入队机制；宏任务与事件循环的整体调度属于宿主环境（Host-defined）行为，浏览器遵循 HTML 规范，Node 则依据 libuv 实现。

### 问题 2：这段代码的输出顺序是什么？为什么？

#### 结论

输出顺序为：

```text
1
4
3
2
```

#### 原理

把代码拆解为带标签的形式逐步跟踪：

```javascript
console.log(1);                                    // ① 同步代码，立即打印 1
setTimeout(() => console.log(2), 0);               // ② 注册宏任务（记作 T1）
Promise.resolve().then(() => console.log(3));      // ③ 注册微任务（记作 M1）
console.log(4);                                    // ④ 同步代码，立即打印 4
```

执行过程：

1. **同步阶段**：主线程从上到下执行 `①` 和 `④`，依次输出 `1` 和 `4`。同时，`②` 将回调注册到宏任务队列，`③` 将回调注册到微任务队列。
2. **微任务清空阶段**：当前同步代码执行完毕（即当前宏任务结束），事件循环检查微任务队列，执行 `M1`，输出 `3`。
3. **宏任务阶段**：微任务队列清空后，事件循环进入下一轮，从宏任务队列取出 `T1` 执行，输出 `2`。

所以最终顺序是 `1 → 4 → 3 → 2`。

这里有两个常见误区必须点破：

- **误区 1**：认为 `setTimeout(0)` 是“立即执行”。实际上 `0ms` 只是“尽早入队”，它仍然排在当前同步代码和所有微任务之后，并且 HTML 规范规定了嵌套超过 5 层时最小延迟为 4ms。
- **误区 2**：混淆“入队顺序”与“执行顺序”。本例中 `T1` 比 `M1` 更早入队，但执行时微任务队列优先，所以 `M1` 一定在 `T1` 之前执行。

验证微任务优先的追加实验：

```javascript
setTimeout(() => console.log('A'), 0);   // 先入宏任务队列
Promise.resolve().then(() => console.log('B')); // 后入微任务队列
// 输出：B 先于 A
```

#### 实现

这道题本质是代码推演题。用一段简化的 JavaScript 伪代码可以更直观地展示“取 1 个宏任务，清空全部微任务”的调度逻辑：

```javascript
// 简化版浏览器事件循环伪代码，帮助理解调度顺序
const macroTaskQueue = [];   // 宏任务队列
const microTaskQueue = [];   // 微任务队列

// 模拟 setTimeout：往宏任务队列尾部追加任务（真实浏览器会处理最小延迟等）
function scheduleMacro(cb) {
  macroTaskQueue.push(cb);
}

// 模拟微任务：往微任务队列尾部追加任务
function scheduleMicro(cb) {
  microTaskQueue.push(cb);
}

// 示例代码的执行标注
console.log(1);
scheduleMacro(() => console.log(2));          // 对应 setTimeout
scheduleMicro(() => console.log(3));          // 对应 Promise.then
console.log(4);

// 事件循环主循环（仅示意，真实浏览器远比这复杂）
while (macroTaskQueue.length > 0 || microTaskQueue.length > 0) {
  // 1. 取出一个宏任务执行
  const macro = macroTaskQueue.shift();
  if (macro) macro();

  // 2. 清空微任务队列（执行中产生的新微任务也会被执行）
  while (microTaskQueue.length > 0) {
    const micro = microTaskQueue.shift();
    micro();
  }
}
// 输出：1 -> 4 -> 3 -> 2
```

#### 边界与追问

- **微任务中抛出异常会怎样？** 如果一个微任务回调抛出异常且未被 `catch`，会触发 `unhandledrejection` / 全局 `error` 事件，但**不会阻止其他微任务的执行**。因此生产环境建议在微任务链尾部显式处理异常。
- **`Promise.resolve().then` 改成 `async/await` 写法会变吗？** 不会。`await` 的后续代码本质上会被包装成一个微任务（Promise Chain），执行时机与 `.then` 一致：

  ```javascript
  console.log(1);
  setTimeout(() => console.log(2), 0);
  (async () => {
    await Promise.resolve();
    console.log(3);
  })();
  console.log(4);
  // 输出：1 4 3 2
  ```

- **追问 1：`setTimeout(0)` 真的是 0ms 执行吗？** 不是。除了等待主线程空闲外，HTML 规范规定嵌套层级超过 5 层后最小延迟提升到 4ms；后台标签页还会被节流（可延时至 1s 甚至更久）。因此不能用 `setTimeout(0)` 来精确测量性能。
- **追问 2：微任务和渲染的先后关系是什么？怎么保证在渲染前完成数据更新？** 微任务队列清空后、进入渲染前，是“更新数据并让 DOM 只被修改一次”的关键窗口。Vue 的 `nextTick` 就利用了这一特性（优先 Promise，降级到 MutationObserver / setTimeout）来保证回调在下次 DOM 更新后执行。在 AI Agent 前端中，面对高频率刷新的流式消息/状态，也常借助这个机制合并频繁的状态变更。
- **追问 3：宏任务执行时间过长会怎样？** 主线程是单线程的，宏任务执行期间，其他宏任务、微任务、渲染都会被阻塞，所以长耗时任务会“卡页面”。对策包括：把大任务拆分为多个宏任务（时间切片），或交给 `Web Worker` 处理（Worker 内没有 DOM，也有自己的事件循环）。

---

## 总结

| 关键点 | 一句话记忆 |
|-------|-----------|
| 微任务 vs 宏任务 | 微任务“立刻清空”，宏任务“每轮取一个” |
| `setTimeout(0)` | 不是立即执行，而是“最早可执行的宏任务” |
| `Promise.then` | 属于微任务，优先级高于任何宏任务 |
| 事件循环本质 | 单线程下的任务调度器，是前端异步、性能优化与框架响应式更新的基础 |
