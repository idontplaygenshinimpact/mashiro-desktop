## 题目

> 解释 React Hooks 的实现原理：为什么 `useState` 不能写在条件语句中，hooks 链表如何工作，闭包陷阱是什么。

这是一道非常经典的 React 原理题，面试官想考察的其实有三层：

1. **你是否理解 Hooks 的底层数据结构（链表）以及为什么“调用顺序”是铁律**；
2. **你是否能讲清楚 hook 在 Fiber 节点上是怎么存储和读取的**；
3. **你是否遇到过闭包陷阱，并知道它的本质和解决方案**。

很多候选人对 `useState` 的 API 倒背如流，但一被追问“为什么不能放 if 里”就卡住；或者能背出“要用 `useRef` 解决闭包问题”，却说不出为什么 `useRef` 能解决。下面一层层拆开讲。

---

### 结论

React Hooks 之所以**不能在条件语句中调用**，是因为 Hooks 在 React 内部是**按调用顺序**依次挂载到一个**单向链表**上的；每次渲染时 React 依赖“顺序”来把当前 hook 的 state 与上一次渲染的 state 对应起来。一旦顺序被打乱（比如某次渲染 if 条件为 false，少调用了一个 hook），链表就错位了，React 会拿错 state 甚至直接报错。

---

### 原理

#### 1. 每次渲染都是一次“从头开始”的执行

函数组件本质是一个普通函数，每次渲染（re-render）都会重新执行一遍函数体。`useState` 在执行时，需要回答一个问题：

> “当前这个 hook，上一次渲染时存的 state 是什么？”

React 在 Fiber 节点上为每个组件维护了一个 **Hooks 链表**，大致结构如下：

```text
Fiber
└── memoizedState（链表头）
     │
     ├── { type: 'useState', memoizedState: 'count值', next: null }   → 第1个hook
     ├── { type: 'useState', memoizedState: 'name值', next: null }   → 第2个hook
     ├── { type: 'useEffect', memoizedState: effect对象, next: null } → 第3个hook
     └── ...
```

关键点在于：**链表里只有数据，没有名字**。React 并不知道你这个 hook 叫 `count` 还是 `name`，它只知道：

- 第一次调用 `useState` → 对应链表第 1 个节点；
- 第二次调用 `useState` → 对应链表第 2 个节点；
- ……

这就是“**靠调用顺序，而不是靠调用名字**”来识别 hook。

#### 2. 为什么条件语句会破坏它

假设组件这样写：

```jsx
function App() {
  const [count, setCount] = useState(0)

  if (count > 0) {
    const [name, setName] = useState('default')
  }

  const [age, setAge] = useState(18)
}
```

- 第一次渲染：`count` 初始为 0，`if` 不成立 → 只调用了 2 个 hook（`useState(0)` 和 `useState(18)`），链表里存了 2 个节点。
- 用户点击使 `count` 变为 1，触发第二次渲染：此时 `if` 成立 → 调用了 3 个 hook。

React 在第二次渲染时，会从链表头开始**逐个配对**：

| React 期望 | 实际调用 | 结果 |
|---|---|---|
| 第 1 个 hook（上次存的 `count=0`） | `useState(0)` | ✅ 正常读取到 0 |
| 第 2 个 hook（上次存的 `age=18`） | `useState('default')` | ❌ 拿到的却是 `18`，类型都变了 |
| 第 3 个 hook（链表里不存在） | `useState(18)` | ❌ 链表走到头了，拿不到 |

React 发现“比预期的多/少”或“节点类型对不上”，轻则 state 错乱（比如 `name` 的值变成 18），重则抛错。

**反过来也一样**：如果第一次渲染调了 3 个 hook，第二次因为条件少了 1 个，链表也会错位。所以 React 官方直接规定：**Hooks 必须放在组件顶层调用，不能放在条件、循环、嵌套函数里**。这也正是 React 18 之后推出 ESLint 插件 `react-hooks/rules-of-hooks` 强制约束的原因——这不是风格问题，是底层数据结构决定了它只能这样。

#### 3. 闭包陷阱的本质

闭包陷阱不是 Hooks 独有的问题，而是 JavaScript 闭包机制在 React 渲染模型下的必然结果。它最常见的场景是：

```jsx
function Timer() {
  const [count, setCount] = useState(0)

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1) // ❌ 每次 count 永远从 0 开始
    }, 1000)
    return () => clearInterval(id)
  }, [])
}
```

原因拆解：

- **闭包捕获的是变量的“值”而非“引用”**（对于基本类型来说）。
- 第一次渲染时，`count = 0`，`useEffect` 里的回调函数创建了一个闭包，捕获了 `count = 0`。
- 因为依赖数组是 `[]`，这个 effect 只执行一次，回调函数**永远不会重新创建**。
- 1 秒后定时器触发时，它访问的 `count` 仍然是那个**旧闭包里的 0**。
- 于是 `setCount(0 + 1)` → 永远是 1。

每次渲染都是独立的“快照”，函数组件里的局部变量在下次渲染时会被重新声明。闭包陷阱的根源是：**你在一个“古老”的渲染快照里，访问了一个本应该随渲染更新的值**。

### 实现

这里给两份关键代码：一份是**简化版 hooks 链表实现**，帮助理解底层；另一份是**闭包陷阱的修复方案**。

#### 1. 简化版：Hooks 链表核心机制

```typescript
// 模拟 React 内部为每个组件维护的 hooks 链表
interface Hook {
  memoizedState: any          // 当前 hook 保存的 state
  queue: any                  // 等待更新的队列（setState 产生的更新）
  next: Hook | null           // 指向下一个 hook
}

// 当前正在渲染的组件对应的 fiber（简化）
let currentlyRenderingFiber: { memoizedState: Hook | null } | null = null
// 链表遍历游标：指向“正在处理的这个 hook”
let workInProgressHook: Hook | null = null

// 模拟 useState 的实现（极度简化）
function useState<S>(initialState: S | (() => S)): [S, (action: any) => void] {
  // 1. 判断是首次挂载（mount）还是更新（update）
  const isMount = workInProgressHook === null

  let hook: Hook
  if (isMount) {
    // 挂载阶段：创建新节点，并追加到链表尾部
    hook = {
      memoizedState:
        typeof initialState === 'function' ? (initialState as () => S)() : initialState,
      queue: null,
      next: null,
    }
    // append 到 currentlyRenderingFiber.memoizedState 链表的尾部（略）
  } else {
    // 更新阶段：直接复用链表中已存在的节点
    hook = workInProgressHook
  }

  // 2. 实现 setState（完整版会计算 queue 里的所有更新，这里简化为直接替换）
  const setState = (action: S | ((prev: S) => S)) => {
    const newState =
      typeof action === 'function'
        ? (action as (prev: S) => S)(hook.memoizedState)
        : action
    hook.memoizedState = newState
    // 触发重新渲染（scheduleUpdateOnFiber，省略）
  }

  // 3. 游标后移：下一次调用 useState 时，就处理链表的下一个节点
  workInProgressHook = hook.next

  return [hook.memoizedState, setState]
}
```

核心结论一目了然：

- **更新阶段完全不看参数 `initialState`**，只用链表里存的旧值；
- 每次渲染都从链表头开始，靠 `workInProgressHook` 这个游标逐个后移；
- 如果某次渲染少调用了一个 `useState`，后面的 hook 全部“错位”——因为连接关系是 `next` 指针串好的，你们抢到了别人的节点。

#### 2. 闭包陷阱的三种修复方案

```tsx
function Timer() {
  const [count, setCount] = useState(0)

  // 方案一：给 setState 传函数（最常见，最佳实践）
  useEffect(() => {
    const id = setInterval(() => {
      setCount(prev => prev + 1)  // ✅ 不依赖闭包里的 count，由 React 在更新时传入最新值
    }, 1000)
    return () => clearInterval(id)
  }, [])

  return <div>{count}</div>
}
```

```tsx
function Timer() {
  const [count, setCount] = useState(0)

  // 方案二：把 count 加入依赖数组，让 effect 重新执行、重新创建闭包
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1)  // ✅ 依赖数组里声明了 count，每次变化都会重建 effect
    }, 1000)
    return () => clearInterval(id)
  }, [count])
}
```

```tsx
function Timer() {
  const [count, setCount] = useState(0)
  const countRef = useRef(count)

  // 同步更新 ref：保证 ref 里永远是“最新值”
  useEffect(() => {
    countRef.current = count
  }, [count])

  useEffect(() => {
    const id = setInterval(() => {
      // ✅ 通过 ref 间接访问最新值，而不依赖闭包捕获的快照
      setCount(countRef.current + 1)
    }, 1000)
    return () => clearInterval(id)
  }, [])

  return <div>{count}</div>
}
```

为什么 `useRef` 能解决？因为 `ref` 对象本身是同一个引用（在组件整个生命周期内稳定存在），你每次渲染时把 `ref.current` 更新为最新值，闭包访问的是 `ref` 对象（引用不变），通过 `ref.current` 拿到的一定是最新的值——**相当于给闭包开了一个“后门”，绕过了快照机制**。

### 边界与追问

#### 边界情况

- **性能**：把 `useState` 写在组件顶层不代表鼓励滥用。每个 hook 都是一个链表节点，hook 数量过多会拖慢渲染时链表的遍历。应通过拆分组件、自定义 hook（`useMemo` / `useReducer` 组合）等方式控制单组件 hook 数量。
- **异常**：React 18/19 的 Concurrent 模式下，组件可能在渲染中途被中断（time-slicing）。React 的做法是：如果 hook 顺序或数量与上次不一致，直接抛出 `Invalid hook call` 错误并丢弃本次渲染，不会默认“默默纠错”。这就是为什么“只在最顶层调用 Hooks”是不可违背的红线。
- **兼容性**：`useState` 的链表机制从 React 16.8 一直到 19 都没有变化过，但内部实现细节有改动（如 React 19 引入了 compiler，自动处理 memoization）。理解“顺序调用”的语义依然有效，且短期内不会移除。
- **替代方案**：`useState` + `useReducer` + 自定义 hook；`useSyncExternalStore` 用于接入外部状态；React 19 的 `use` 也遵循同样的调用顺序约束。

#### 面试官可能追问的问题

**Q1：`useState(initialState)` 里传的是函数，和传值有什么区别？**

A：传函数时，React 在首次渲染时调用它来获取初始值，这就是 **惰性初始化（lazy initial state）**，适合初始值计算成本较高的场景（比如从 localStorage 读数据、做复杂运算）。但要注意：这个函数只在首次渲染时执行一次，后续更新会直接忽略它。

**Q2：`setState` 传入对象和传入函数，区别是什么？**

A：传入函数 `setCount(prev => prev + 1)` 时，React 会把多个更新“排队”依次执行，同一个事件里的多个 `setCount` 会累加；传入普通值时，后面的会覆盖前面的。且函数式更新不依赖闭包里的旧值，天然规避闭包陷阱。

**Q3：`useEffect` 的依赖数组为什么不能省略（在非必须时）？**

A：省略依赖数组意味着每次渲染都重新执行 effect，会和「函数式组件每次渲染都创建新闭包」的特性叠加，造成不必要的重复监听、内存泄漏风险。正确做法是：

- 不依赖任何值 → `[]`，但要注意闭包陷阱；
- 依赖某个值 → 显式列出来，让 effect 随该值变化而重建（React 19 的 compiler 可以自动推导依赖，替代手动维护）；
- 需要读取最新值且不想重建 effect → 通过 `useRef` 或函数式 `setState` 绕过。

**Q4（扩展考点）：`useCallback` / `useMemo` 也受同样的规则约束吗？**

A：完全一样。它们也是通过链表节点的顺序来定位的，所以也**不允许出现在条件语句中**。很多候选人知道 `useState` 不能放 if 里，却漏了 `useCallback`、`useMemo`、`useRef`、`useEffect`——所有 Hooks 一视同仁。

---

**最后总结一句给面试官的“一句话回答”**：Hooks 靠“调用顺序”在 Fiber 的链表中定位状态，所以必须无条件在顶层调用；闭包陷阱本质是每次渲染都是独立快照，旧闭包引用旧值，用函数式更新或 `useRef` 就能绕开快照取到最新值。
