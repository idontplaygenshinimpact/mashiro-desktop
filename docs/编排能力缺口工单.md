# 编排能力缺口工单（排期：P0/P1 治理之后）

> 依据 `docs/架构评审报告-2026-09.md` §2.2/§3：编排层"治理 ≈ 一线水准、智能编排中等偏基础"。
> 本工单覆盖 4 个已确认缺口：规划状态机 / 失败反思 / 模型路由 / 记忆检索注入。
> **执行顺序：排在 P0-1（双层权限脱节）、P0-3（注入检测未接线）、P1-1（面试会话治理）之后。**

---

## 为什么排在治理之后（依赖论证）

1. **T1 要新增/改造工具**（plan/todo 语义升级）——P0-1 不修，新工具会继续踩"policy confirm 但运行时 auto"的双层脱节，权限语义不稳定时叠加新编排逻辑 = 在漂移地基上盖楼；
2. **T4 要把外部内容接进记忆检索链**——P0-3（`sanitizeExternal` 的 injections 检测全库被忽略）不修，抓取内容进检索/注入链有注入放大风险；
3. **T1 的计划状态与会话状态耦合**——P1-1（会话无 idle 超时、无 id 单例、双路径竞态）不修，计划状态会叠加同样的竞态。

## T1 规划执行状态机（~1.5-2 天）

**现状底座**（有证据的可用资产）：
- `lib/todo.mjs` 已持久化到 settings 表（todo.mjs:3,10,21）——任务清单存储可用
- `plan_mode`（exec-tools.mjs:222-243）+ `ask_user`——用户确认关卡已有
- `interview-session.mjs` 的 `advanceRound` 三态推进（session:114-192）——状态机先例
- `plan_task` 工具（agent.mjs:247-248）——但只是"口头承诺"，计划不持久化、步骤无状态

**缺口**：复杂任务"先计划后执行"靠 LLM 自觉（system prompt 第 1 条口头要求），跨轮无计划对象。

**方案要点**：
1. 对话级计划对象 `PlanStore`（id/目标/步骤[{title,done}]/currentStep/状态）：`plan_task` 写库；
2. 强制两阶段：`plan_task` 后 LLM 必须先 `plan_mode` 确认再执行；每完成一步 `todo_done` 推进 currentStep；
3. system prompt 注入当前计划状态（第 N/M 步），防 LLM 中途跑偏；
4. 新对话不继承计划（会话重置，与 permission 会话重置同口径 agent.mjs:368-375）。

**验收**：多轮对话 + 进程重启后计划状态可恢复；工具循环中 LLM 擅自跳过未完成步骤时被提示纠正；`npm test` 新增 plan 状态机测试（创建/推进/取消/恢复）全绿。

## T2 失败反思机制（~1-1.5 天）

**现状底座**：
- `withRetry` 只重试瞬时错误（exec-utils.mjs:10-18 isTransientError）
- 工具失败回填 `{error, hint}` 结构；死循环/连续失败护栏已按工具独立计数（agent.mjs:415-533）
- 错误已粗分类：`validateArgs` 参数错 / 权限拒绝 / 策略拦截 / MCP 异常 / 执行异常（agent.mjs:187-345）

**缺口**：没有"错误分类 → 自动换策略"的编排动作——`job_search_platform` 网络失败与参数错误走同一条"回填 error 等 LLM 自行处理"，LLM 常重复犯同类错直到触发失败护栏。

**方案要点**：
1. `executeTool` 返回规范化 `{error, kind}`（param/perm/transient/hard）；
2. 主循环加失败处理表：`param`→注入"检查参数再调"；`transient`→自动重试（withRetry 已有，提升上限）；`perm`→注入"换只读方案"（会话 deny 已拦截，补充策略提示）；`hard`→收束；
3. 连续失败注入"换策略提示"（现有 hint 文案升级），减少无谓重试消耗。

**验收**：bench:agent 故障注入场景（参数错/网络断/权限拒）通过率不降 + 重试次数下降可观测（trace_tools）；新增单测：每类错误走正确分支；LLM 重复同类错误次数 ≤ 现状。

## T3 模型路由（~1 天）

**现状底座**：
- `llm.mjs` role 参数全链路已贯通（agent/subagent/loop/review/interview 均传 role）——**但只进审计表**（llm.mjs:95,300），不驱动任何选择
- `config.providers` 多 provider（config.mjs:56-86）+ 双端点 failover（llm.mjs:104-276）
- `eval-cost.mjs` 成本/延迟计量已有

**缺口**：小任务（分类/提炼/挑帖）与大任务（讲解/编排）同模型同参数，成本无差异化。

**方案要点**：
1. llm.mjs 加 `ROLE_TIER` 映射：`role=classify/refine/detect` → 便宜档（maxTokens/temperature 收紧；可用小模型端点）；`role=agent/solve/interview` → 完整档；
2. 与 failover 兼容：小档失败仍走主端点重试链（不改 llm.mjs:122-276 现有尝试顺序）；
3. eval-cost 按 role 分组展示，落地成本对比数据。

**验收**：eval-cost 报表显示分类/讲解成本分化；bench:agent 全量通过率不降（judge 口径）；typecheck 0、npm test 绿。

## T4 记忆检索注入（~1 天）

**现状底座**：
- `similarity.mjs` 规则分层 + LLM 兜底（similarity.mjs:40-215）——检索打分可直接用
- `memory.getCuratedMemory`（memory.mjs:448-464）——curated 表已持久化
- `get_memory` 工具（agent 显式调用）——但不会自动注入

**缺口**：
- `injectCuratedIntoPrompt(content, 8)` 是**固定 top-8 排序注入**，与用户当轮问题无关（memory.mjs:467-473）
- P1-7：先 LIMIT 再 filter untrusted，前 8 含不可信来源时不补足（memory.mjs:450-469）

**方案要点**：
1. `chatWithAgent` 用户消息 → `similarity` 对 curated/薄弱点/近期对话检索 top-k（k 按预算，≤8）动态注入；
2. 无命中时保留现有固定 top-8 兜底（行为兼容）；
3. 顺带修 P1-7：先 filter untrusted 再 LIMIT。

**验收**：基准用例（问"简历项目"→相关记忆优先注入；问"复习进度"→薄弱点/复习条目优先）；新增单测：query 相关条目排序在无关条目前；既有对话行为无回归（npm test）。
