## 工作流程（必须遵守）

### 阶段 1：通读与现状梳理（不写代码）
1. 按上面顺序读文档与源码，建立"现有架构地图"：
   - 分层结构（渲染层 / IPC / widget 路由 / 业务 lib / 插件 / 数据层 / 外部集成）
   - 数据流（请求链路、事件流、回流闭环：薄弱点→复习卡→面试→清单）
   - 每个核心模块的职责与依赖方向（谁 import 谁，循环依赖在哪）
2. 输出**架构现状图**（文字拓扑即可）：模块清单 + 依赖关系 + 数据流方向 + 已知债务（如散落的重复实现、越层调用、循环依赖、耦合点）

### 阶段 2：架构评审（不写代码）
识别问题，按严重度分级（P0 架构风险 / P1 明显债务 / P2 可优化），每个问题必须附：
- **代码证据**（文件:行号 或 git log 佐证）
- **影响面**（哪些功能/模块受影响，用户可感知的现象）
- **根因**（设计时的取舍，还是演进中长歪的）

重点审查维度：
1. **分层与依赖**：lib 层是否纯净（不反向依赖路由/渲染）？插件机制是否稳定？循环依赖怎么处理？
2. **数据一致性**：多写路径（widget/插件/测试）是否共享同一 schema 迁移？内存镜像 vs DB 的同步策略？
3. **并发与状态**：流式链路的超时/防重入/代际管理、后台任务的门控与互斥、单实例锁
4. **可测试性**：测试覆盖的盲区（mock 盲区、时序偶发、集成覆盖）
5. **演进合理性**：现有设计是否还有扩展空间（新方向/新渲染层/新插件），还是已经焊死
6. **性能与资源**：O(N) 扫描、内存驻留（embedding/模型）、LLM 调用成本

### 阶段 3：升级改造方案（输出方案，等确认后再实施）
基于现状评审，输出**升级路线图**（分阶段）：
- **每个阶段的改造必须**：
  - 有明确目标（解决哪个 P0/P1 问题）+ 验收标准（可验证的数字/行为）
  - 是**渐进式**的（不破坏现有测试与行为，先加后改，保持兼容）
  - 有风险清单（改什么会破什么，怎么回滚）
- 方案要**克制**：不做无收益的"架构洁癖"改造；优先解决用户可感知的问题与面试拷问点
- 第一批改造任务：选出 1-3 个投入产出比最高的，写成可直接执行的工单（含任务拆分/验收/测试要求）

### 阶段 4：实施（按确认的方案）
- 每个改动遵循项目红线：npm test 全绿、lint 0 error、typecheck 0
- 改动前先看该模块的测试（tests/），保证行为兼容；行为变化必须更新测试并说明理由
- 每完成一个阶段：跑全量回归 + 提交（commit message 说明动机与证据）
- 涉及渲染层改动：确认构建产物（panel-vue-review/panel-react 需各自 build）与 widget 重启

## 红线（违反即返工）

1. **不推倒重来**：现有架构是踩坑演进的，升级是在其上加固；除非证据确凿否则不迁移/重写既有模块
2. **不留假绿**：测试必须真实覆盖（mock 队列空会抛错防假绿——不许绕过）、不批量 eslint-disable、不 tsconfig exclude
3. **每个决策有证据**：说"这里有问题"必须给文件:行号；说"这样改更好"必须给验收标准
4. **保持兼容**：ESM import 路径、IPC 方法名、API 响应结构、DB schema 迁移（只 ADD 不破坏）
5. **增量提交**：每阶段一个 commit，可回滚
