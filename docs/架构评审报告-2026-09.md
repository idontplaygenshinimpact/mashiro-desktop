## 3. 问题清单

### P0（架构风险/安全边界）

**P0-1 双层权限脱节：policy"confirm"与运行时"auto"不一致，未列工具静默直放**
- 证据：tool-policy 语义"confirm 需运行时审批"（tool-policy.mjs:6,16），但运行时只认 TOOL_PERMISSIONS 的 4 项 confirm（agent.mjs:36-47,119-140）；browse_*、job_search_platform、spawn_subagent 等大量未列工具**静默 auto 执行无审批**
- 影响面：治理宣称与真实行为不符；写库/外部副作用工具（job_search_platform 写 job_posts、browse 交互）无人工关卡；面试拷问"权限体系一致性"时防线塌方
- 根因：两套权限系统（policy 层 + 运行时层）演进未同步

**P0-2 schema 迁移无版本化框架 + 迁移错误静默吞掉 → Schema 漂移风险**
- 证据：`CREATE TABLE IF NOT EXISTS` 基座 + `user_version=1` 写死（db.mjs:309），schema_meta 仅记账（:332-335）；补列散落 db.mjs:313-353 + jobs.mjs:28-48 + focus.mjs:23 + rag.mjs；`try{...}catch{/* 迁移失败不阻断 */}` 吞错（db.mjs:313-319）
- 影响面：旧库升级不可追溯；列缺失只在运行时炸；"表存在但列缺"的隐蔽态
- 根因：演进期 ad-hoc 补列，未建立迁移框架（与 45K 行平铺演进史一致）

**P0-3 注入检测结果全库被忽略（prompt 注入防护只剩包裹层）**
- 证据：`sanitizeExternal` 返回 `{wrapped, injections}`，全库调用点只取 `.wrapped`（prompt-guard.mjs:48-51；ai.ts:65-67；job-match.mjs:87 等）；`injections` 检测形同摆设
- 影响面：外部内容里的指令注入能被检测但从未被阻断
- 根因：API 设计返回了检测结果，消费端未接（一次性包装后无人补）

## 6. 评审结论

1. **架构成熟度**：治理型能力（权限/审计/防注入/防失控/评测闭环）是**真实可信的强项**，代码与测试双重支撑，远超一般个人项目；编排智能（规划/反思/路由/检索）是真实的缺口——与"agent 是核心卖点但没搞好"的判断一致，且现在有了证据化的差距清单。
2. **最值得先修的 3 件事（ROI 排序）**：
   - ① P0-1 双层权限脱节（~0.5 天）：运行时统一读 tool-policy 的 confirm 集合，或给 browse/job_search 显式登记 TOOL_PERMISSIONS——治理宣称与行为对齐；
   - ② P0-3 注入检测接上（~0.5 天）：sanitizeExternal 调用点把 injections 非空时降级/截断，堵住"检测了不阻断"；
   - ③ P1-1 面试会话治理（~1 天）：idle 超时 + 会话 id 化，消除双路径竞态。
3. **与本轮 TS/Bun 结论的闭环**：P0/P1 全部是**逻辑与治理问题，与运行时无关**；而 71 个 lint warning（含死导入）和 1058 用例的维护正是 TS 渐进迁移（P0：agent.mjs/permission/tool-policy）的理由——运行时留 Node 的结论在本轮审计后反而更强。
4. **数字校准**：343 个 .mjs / 3 个 .ts / 114 测试文件 / 1058 用例（文档多处过期，建议统一台账）。
