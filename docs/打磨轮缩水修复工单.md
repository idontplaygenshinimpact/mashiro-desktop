# 打磨轮缩水修复工单（工单 v3——修正者保持完整性 + 打磨后结构检查）

> 背景：subagent 打磨循环（工单 v2——多轮打磨/上下文累积/角色分离/few-shot）已实现并工作（3 轮修正 R1→14869/R2→14998/R3→14096）——但**验收发现"缩水"**：草稿 28728 字符 → 打磨后 14096（字符少一半 + 模拟面试问答部分丢失）。根因：修复者 context 截断（看不到完整草稿）+ "重写整篇"丢已有内容 + 打磨后无结构检查。要求：**修复缩水——打磨轮"只补差距不缩水"——打磨后结构完整**。

---

## 一、验收发现的问题（修复目标）

| 问题 | 现象 | 根因 |
|---|---|---|
| **① 打磨轮缩水** | 草稿 28728 → 打磨后 14096（少一半） | 修正者 context 只带草稿前 14000 字符（看不到完整草稿）——基于截断重写→简化 |
| **② 部分丢失** | 模拟面试问答部分没了 | 修正者"重写整篇"（不是"补差距"）——重写时丢已有内容 |
| **③ 无结构检查** | 问答丢了没发现/没补 | 打磨循环没有"打磨后结构检查"环节 |
| **④ npm test 卡住** | 120s 超时（环境问题） | 待排查（可能是残留进程/测试卡住） |

## 二、实现任务

### 任务 1：修正者 context 不截断（保持完整性）

```
修复 skill.mjs 打磨循环的修正者：
- context 从"草稿前 14000"改为不截断（或分步修正——每部分单独带全文修正）
- 分步修正方案（推荐）：打磨差距涉及哪些部分 → 只修正对应部分（带该部分全文）→
  其他部分原样保留（拼接）——**不重写整篇**
- 或者：context 上限提高（maxContext 20000 → 更大——草稿全量）
- 修正者 system 明确："保持所有部分完整——只补差距不删已有内容"（防缩水）
```

### 任务 2：修正者"补差距"模式（不是重写整篇）

```
- 修正者 task 明确："**只修改差距清单涉及的部分**——其他部分原样保留（不重写/不删除）"
- 输出格式：修正后的完整文档（但只在差距部分改动——其余原文保留——字符不缩水）
- 修正者输出后校验：字符 ≥ 输入草稿的 80%（缩水预警——低于则重试/保留草稿）
```

### 任务 3：打磨后结构检查（新增）

```
打磨循环结束后（或每轮修正后）：
- 结构检查器对照质量标准清单逐项：
  □ 背诵路线图 □ 一句话定位 □ 关键设计决策 □ 源码要点
  □ 八股 □ 模拟面试问答 □ 可能的追问 □ 怎么讲（讲述脚本/技巧）
- 缺的部分 → 自动补（派补缺 subagent——生成缺失部分——插入对应位置）
- 全部在 → 达标存档
```

### 任务 4：npm test 排查

```
- 排查 npm test 120s 超时（残留进程/测试卡住——定位卡住的测试）
- 修复后 npm test 全绿
```

## 三、验收

- [ ] 打磨后字符 ≥ 打磨前草稿（不缩水——或缩水 <20%）
- [ ] 结构全覆盖（打磨后所有部分都在——含模拟面试问答/可能的追问/讲述技巧）
- [ ] 修正者 context 不截断（或分步修正——保持完整性）
- [ ] 打磨后结构检查（缺的部分自动补）
- [ ] 生成文档 ≥50000 字符（打磨后不缩水——接近标杆）
- [ ] `npm test` 全绿 + lint 0 + typecheck 0

## 四、红线

1. 真实源码（不编造文件名/代码）
2. 八股准确（不幻觉）
3. **不缩水**（打磨轮只补差距——已有内容原样保留）
4. 结构检查后补缺（不删已有——只加缺的）
5. 轮数上限 3（不无限打磨）

## 五、工作量

- 任务 1（context 不截断/分步修正）：半天
- 任务 2（补差距模式 + 缩水校验）：半天
- 任务 3（结构检查 + 补缺）：半天
- 任务 4（npm test 排查）：1 小时
- **合计：约 1.5 天**

## 六、面试价值

> "打磨轮验收发现'缩水'：草稿 28728 打磨后 14096——**修复者 context 截断（看不到完整草稿）+ 重写整篇丢已有内容**。修复：**修正者'补差距模式'（只改差距部分——其余原样保留）+ context 不截断 + 打磨后结构检查（缺的自动补）**。**打磨的本质是'补差距'不是'重写'——重写会把好内容也弄丢。**"
